This project uses .NET 9.0 and is configured as a full-stack (API, UI) application.
It supports search and vector search using PostgreSQL, and also enables vector search using Neo4j.

We aim to implement an ASKBot feature that creates a conversational chatbot for searching memories interactively step-by-step. Please add new features according to the following requirements.

## Stage 01 - Actor Model Design and Implementation

### Guidelines
- Create a ChatBotActor actor model that is instantiated per user session.
- The ChatBotActor will be connected to SSE and will process user conversation requests and stream responses via SSE. SSE implementation is not required immediately; implement the actor model to provide streaming-style responses.
  - One ChatBotActor corresponds to each user session. Reuse the same actor if the same session exists.
  - ChatBotActor automatically terminates after 3 days of no conversation per session. This is for system resource conservation to clean up chatbot session-related memory. - Use timer within the actor
  - SearchMemoryActor and DecisionActor described below are pre-created, and ChatBotActor uses these created reference actors. The created reference actors are passed when ChatBotActor is created.
- SearchMemoryActor handles memory search. It can use LLM to determine if search is needed for requests and transforms them into natural language sentences suitable for search to find related content. IT-related terms are converted to English words.
  - Memory can be searched using src/Memorizer/Services/Memory.cs.
  - When memory search is not needed for a request, it responds with no search results without attempting to search.
  - Memory search can perform similarity search by sentence, using up to 5 results with similarity above 0.3.
    - If there are no search results, extract keywords from the attempted sentence and retry up to 3 times in English and Korean.
  - LLM can be used to achieve this actor's purpose, and prompts are written within the actor model.
- DecisionActor determines whether the request content and search results are relevant.
  - If determined relevant, generates a response using search results as related documents.
  - If determined not relevant, responds with no related documents.
  - LLM can be used to achieve this actor's purpose, and prompts are written within the actor model.
- ChatBotActor uses SearchMemoryActor and DecisionActor to generate responses for various user conversation requests.
  - When DecisionActor cannot find related materials for the request, generates a general LLM response.
  - ChatBotActor can generate general responses using LLM.
  - ChatBotActor determines whether the response content is from source memory or general and generates the response. It can additionally express referenced locations.
  - ChatBotActor can receive the reasoning process from other actors until the final response. This process should be expressible through SSE streaming later. SSE streaming is not implemented immediately.

## Local Testing Method
- Can test locally through docker-compose.local-psmon.yml. Use this file for Docker operation issues.
- This application is built and operated through memorizer. Use Docker only when rebuild/restart is needed.
- During test improvements, DB schema changes are not allowed, only READ is permitted, postgres and neo4j are Docker-based and working well, do not stop or take them down.
- For actor model unit test methods, refer to the following. When creating an actor model, write or update unit tests for that actor.
  - Actor model unit test method: https://mcp.webnori.com/ui/view/7a525e7f-dfed-4b38-bb4c-2de6e77d1cea

## Additional Guidelines - Integration Testing Using Actual Devices Instead of Mock Testing
- Using src/Memorizer.IntegrationTests/appsettings.json settings... testing with actual devices instead of Mock testing... Since LLM responses are unpredictable, only check if response format is correct rather than Assert... probe can be set after telling for test execution.. probe can be used for checking reception during test verification only when present. This is for actually checking if response quality is good when attempting various request scenarios to ChatBotActor, and evaluation of final results can be confirmed through unit test result console rather than assert.
