  - 이미 생성된 이벤트 스토밍,예제맵핑,보완된 PRD 결과를 참고해 BC를 도출합니다.

  - 목표에 맞는 프롬프트 설계를 하며 다음 바운디드 컨텍스트 정의 지침을 참고합니다.
    - 서브도메인 분해,유비쿼터스 언어 충돌,변경 이유,트랜잭션 경계,데이터 소유권,조직 경계 등 다양한 기준을 활용하며 설명을 포함합니다. 

### 바운디드 컨텍스트(BC) 정의 지침
```
2) 서브도메인 분해(Strategic DDD): Core / Supporting / Generic
먼저 비즈니스를 서브도메인으로 나누고, 각 서브도메인에 BC를 매핑하는 방식입니다.
Core: 경쟁우위/차별화 영역 → 모델을 깊게, 독립적으로
Supporting: 핵심을 돕는 업무 → 비교적 단순/유연
Generic: 범용(로그인, 알림 등) → 패키지/외부 서비스도 고려
👉 보통 Core는 BC를 더 잘게/명확히 나누고, Generic은 통합/외부화가 잦습니다.
3) “유비쿼터스 언어(용어)” 충돌로 경계 잡기
같은 단어가 팀/업무에 따라 의미가 다르면 BC 분리 신호입니다.
예: **“정산”**이
결제팀: PG 기준 결제 정산
판매팀: 매출/수수료/프로모션 반영 정산
회계팀: 회계 전표/마감 기준 정산
→ 이름은 같지만 모델이 다르면 서로 번역(컨텍스트 매핑) 관계로 두는 게 안전합니다.
4) 변경 이유(Why it changes) 기준으로 자르기
BC는 “데이터”보다 **변경의 이유(규칙이 바뀌는 축)**가 중요합니다.
할인 정책이 자주 바뀌고 실험이 많다 → “가격/프로모션” BC 분리 후보
배송사는 바뀌지만 주문 규칙은 안정적 → “배송 연동”은 별도 BC/어댑터로
5) 트랜잭션/일관성 경계로 자르기 (강한 힌트)
“한 번에 같이 저장/롤백되어야 하는 것”이 많으면 같은 BC일 가능성이 큽니다.
강한 일관성(즉시 일치)이 꼭 필요한 것끼리 묶고
그 외는 도메인 이벤트 + 최종적 일관성으로 분리하기 좋습니다.
예: 주문 생성(주문 BC) ↔ 결제 승인(결제 BC)은 이벤트로 연결되는 경우가 많음.
6) 데이터 소유권(Ownership)과 쓰기 모델 기준
“누가 이 데이터를 쓴다(write)?”를 기준으로 소유 BC를 정합니다.
다른 BC는 가급적 직접 수정하지 않고
조회는 복제(read model)하거나
이벤트/ACL(Anti-Corruption Layer)로 가져옵니다.
7) 조직/팀 경계(Conway’s Law)를 ‘참고’로 활용
현실적으로 팀이 다르면 릴리즈/우선순위/용어가 갈라져 BC도 갈라지는 게 자연스러운 경우가 많습니다.
다만 “조직이 나뉜다 = 무조건 BC 분리”는 위험
→ **결합도(변경/트랜잭션/용어)**가 함께 맞을 때만 분리를 확정하는 편이 좋습니다.
빠른 체크리스트 (BC 분리 후보 신호)
아래 중 2~3개 이상 해당하면 분리 후보로 강하게 봅니다.
같은 용어가 다른 의미로 쓰인다(언어 충돌)
규칙/정책이 자주 바뀌는 축이 다르다(변경 이유 분리)
배포 주기/담당 팀이 완전히 다르다
강한 트랜잭션으로 묶일 필요가 없다(이벤트로 충분)
외부 시스템 연동이 많아 “어댑터/ACL”로 격리하고 싶다
데이터의 write 주체가 분리되어 있다(소유권)
흔한 실수 3가지
DB 테이블 기준으로 자르기: 테이블은 구현 결과라 도메인 경계와 어긋나기 쉬움
너무 미세하게 쪼개기: 이벤트/통신/운영 복잡도만 커짐
공유 모델 강요: BC의 핵심은 “같은 언어/같은 모델”인데, 공유하면 충돌이 누적됨
```
